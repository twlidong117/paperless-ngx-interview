# 第二步：把教学规则和进度保存进仓库

日期：2026-09-07。本讲义由 Codex 辅助生成。

## 目标与原因

让后续 Codex 会话读到固定教学要求和实际进度，减少换对话后重复解释、跳过基础或误判完成状态的问题。

## 新名词

- 根目录：项目最外层目录。
- AGENTS.md：Codex 可以读取的项目工作说明文件；文件名必须准确保留。
- Markdown：用普通文本表示标题、列表和链接的文档格式，扩展名为 .md。
- 学习进度：记录哪些步骤已经完成、证据是什么、下一步是什么的文档。
- 提交：将这一组文件变更保存为一条可追溯的历史记录。
- 验收：依据预先定义的条件判断操作是否达到目标。
- Codex 云端环境：远程运行 Codex 任务的工作空间，包含项目代码和任务需要的软件配置；它的建立与应用成功运行需要分别验证。

## 具体操作

执行者：助手；位置：用户自己的 GitHub 仓库的开发分支。

1. 核实根目录没有现成 AGENTS.md，也没有 learning 学习目录，避免覆盖已有资料。
2. 阅读原项目贡献说明，再把已准备的教学约定更新为真实仓库状态。
3. 新增 AGENTS.md，保存逐步教学、名词解释、完整名称、每步问答和实际证据要求。
4. 新增 learning/PROGRESS.md，记录第一步已完成、Codex 连接与应用运行仍待验证。
5. 新增第一步和第二步讲义，保存操作原因、知识点、文档、面试题和参考答案。
6. 将上述四份文件作为同一次提交写入，并在提交后读取远程文件核对。

这里的 learning 表示学习，PROGRESS 表示进度，steps 表示步骤。目录名称用于整理资料，本身不会自动让 Codex 读取；AGENTS.md 明确要求先读取进度和最近讲义。

## 验收与边界

本提交提供四份教学文件。发布后的验收方式是：读取开发分支最新记录和新增文件，核对四份文件内容与预期一致，确认其余文件保持原来的内容标识。

当前尚未在用户的 Codex 中启动新任务，因此“Codex 已加载教学规则”和“应用运行成功”都不是本步成果。需要下一步实际读取才能确认。

## 知识点总结

- 项目规则与学习进度需要一起保存，前者规定工作方式，后者记录真实状态。
- 项目根目录中的 AGENTS.md 是 Codex 支持的说明入口。
- 有文档不等于已执行，有代码不等于可运行。
- 一次提交可以保存一组相关文件，便于定位本次改动。
- 后续面试材料应明确区分原项目能力与个人新增成果。

## 面试题与参考答案

**问题一：为什么不只把要求留在聊天记录里？**

项目内文档可随代码保存和追踪，新的工作会话能读取规则与实际进度，减少依赖旧对话。文档仍需及时维护，不能自动保证准确。

**问题二：AGENTS.md 与学习进度有什么区别？**

前者说明 Codex 应怎样工作，例如先解释后操作；后者说明已经完成什么、证据在哪里、下一步做什么。二者配合才能既保持教学方式，又继续正确的步骤。

**问题三：如何验证 Codex 已经正确接入项目？**

让它实际读取项目文件，报告仓库、分支、教学规则和当前进度，并指出具体依据。仅能打开网页或在当前聊天读取 GitHub，不能证明另一个 Codex 任务已接入。

## 可选练习

如果 Codex 说“看到配置文件，所以程序已经运行成功”，你应该要求它补充什么证据？

参考：实际启动结果和功能检查结果，例如访问页面或执行明确的测试；配置文件只能证明存在配置。

用户打开 https://chatgpt.com/codex ，连接 GitHub 并允许访问自己的仓库，创建或选择该仓库的云端环境，在开发分支发起一次读取教学规则的任务。具体界面若不同，应根据实际页面指导。本步不要求运行应用或安装全部依赖。
